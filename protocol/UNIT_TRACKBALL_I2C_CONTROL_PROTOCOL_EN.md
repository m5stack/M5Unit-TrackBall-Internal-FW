# Unit TrackBall I²C Control Protocol (Firmware `0x01`)

## 1. Basic Information

| Item | Description |
| :--- | :--- |
| Bus | I²C |
| Default I²C address (7-bit) | `0x3F` |
| Configurable I²C address range (7-bit) | `0x08 ~ 0x77` |
| Bus speed | Supports `100 kHz` and `400 kHz`; the bus clock is generated by the host |
| Register address width | `8 bit` |
| Register data width | `8 bit`; multi-byte data is made up of consecutive registers |
| Multi-byte endianness | Little-endian (low byte at the lower address) |
| Firmware version | `0x01` |
| Invalid read return value | `0xFF` |

### 1.1 Bus Mode and Rate

The device operates as an I²C **slave**, and the external host is responsible for generating SCL. The I²C slave interface of the current firmware handles address matching, byte reception/transmission, STOP, NACK and bus errors in interrupt mode, and clock stretching is enabled. The host can therefore access the same register protocol at `100 kHz` or `400 kHz`; the register addresses, data formats and transaction timing remain unchanged.

Both `100 kHz` and `400 kHz` are within the supported range, but the achievable rate still depends on the host, pull-up resistors, bus capacitance, wire length and supply voltage. When using `400 kHz`, make sure the SDA/SCL rise times and waveforms meet the I²C Fast-mode electrical requirements. The host must send a proper STOP in every transaction, or use a REPEATED START for combined reads as described in this document.

### 1.2 Access Permissions

| Permission | Meaning |
| :--- | :--- |
| `R` | Read-only |
| `W` | Write-only |
| `R/W` | Readable and writable |
| `R/C` | Cleared automatically after read |
| `Reserved` | Reserved; must not be accessed |

### 1.3 Read/Write Transactions

#### Register Read

A combined transaction is recommended:

```text
START -> SLA+W -> Register Address -> REPEATED START -> SLA+R -> Data... -> NACK -> STOP
```

Alternatively, the register address can be sent and the write transaction terminated, followed by a separate read transaction. The host must first write the 1-byte register address; direct reads without specifying a register address are not supported.

When reading starts from any address within a contiguous register group, the device returns data from that address up to the end of the current group in ascending address order. Beyond the readable length of the current group, subsequent bytes return `0xFF`. For example, starting at `0x01`, at most 3 bytes (`0x01 ~ 0x03`) can be read.

#### Register Write

A single write transaction has the following format:

```text
START -> SLA+W -> Register Address -> Data -> STOP
```

Regular registers accept only 1 byte per write. The following register groups additionally support contiguous read/write starting from any address within the group. On contiguous writes, the device validates and processes each register one by one in ascending address order; when the data for one register is invalid, only that register is ignored and processing of the other registers in the same transaction is unaffected. `0x30 ~ 0x35` is a cross-register key timing parameter group and is still validated as a complete parameter set; see `4.6`:

| Address group | Name | Permission | Description |
| :--- | :--- | :--- | :--- |
| `0x30 ~ 0x35` | Key Timing | R/W | Contiguous read/write of key timing configuration |
| `0x40 ~ 0x41` | Sensor Reinitialize / Clear Data | W | Contiguous write of command registers (write-only; reads return `0xFF`) |
| `0x50 ~ 0x51` | Axis Configuration / I2C Error Count | R/W | Contiguous read/write of axis configuration and error count |

When reading or writing contiguously from any address in a group, the device returns or updates data from that address to the end of the register group; a write must not go past the group end. Except for the complete parameter-set validation of `0x30 ~ 0x35`, the write result of each register is independent.

## 4. Register Details

### 4.1 Trackball Motion

| Address/Range | Length | Permission | Function |
| :--- | :--: | :--: | :--- |
| `0x00 ~ 0x03` | `4 byte` | `R` | Returns the most recently sampled X/Y motion data |

#### Parameters

| Address/Offset | Name | Value/Range | Default | Description |
| :--- | :--- | :--- | :--- | :--- |
| `0x00` | `DX_L` | `0x00 ~ 0xFF` | `0x00` | Low byte of X motion |
| `0x01` | `DX_H` | `0x00 ~ 0xFF` | `0x00` | High byte of X motion |
| `0x02` | `DY_L` | `0x00 ~ 0xFF` | `0x00` | Low byte of Y motion |
| `0x03` | `DY_H` | `0x00 ~ 0xFF` | `0x00` | High byte of Y motion |

#### Data Format

`DX` and `DY` are both little-endian `int16_t`:

```c
int16_t dx = (int16_t)((uint16_t)data[0] |
                       ((uint16_t)data[1] << 8));
int16_t dy = (int16_t)((uint16_t)data[2] |
                       ((uint16_t)data[3] << 8));
```

The sensor always operates in Active mode with 12-bit motion resolution, and the firmware stores the sign-extended result as `int16_t`. By default the user coordinate system has neither X nor Y inverted and does not swap the axes; the firmware automatically maps the user configuration onto the sensor's internal direction configuration.

#### Notes

1. Reading the motion registers does not automatically clear `Data Ready`; reading register `0x10` clears the current ready flag.
2. The firmware keeps only the most recent sample and provides no motion queue; a new motion sample may overwrite an older value that has not been processed yet.
3. Read 4 bytes starting at `0x00` to obtain `DX/DY`; `Data Ready` must be read separately from `0x10`.

### 4.2 Data Ready

| Address/Range | Length | Permission | Function |
| :--- | :--: | :--: | :--- |
| `0x10` | `1 byte` | `R/C` | Indicates whether new motion data has been sampled; cleared on read |

#### Parameters

| Address/Offset | Value/Range | Default | Description |
| :--- | :--- | :--- | :--- |
| `0x10` | `0` | `0` | No new motion data pending |
| `0x10` | `1` | `0` | New motion data available; the firmware sets it to `1` when valid motion is sampled |

The normal handshake is: read `0x10`; when it returns `1`, the flag is cleared automatically once that read completes; the host then reads `0x00 ~ 0x03` to process `DX/DY`. If the firmware samples new motion during the read, `Data Ready` stays `1` and is not cleared by the older read. Write requests to `0x10` are ignored.

When reading 3 bytes starting at `0x10`, the return order is `Data Ready`, `Key State`, `Key Event`. Reading only the first 1 or 2 bytes does not clear `Key Event`.

### 4.3 LED PWM Duty

| Address/Range | Length | Permission | Function |
| :--- | :--: | :--: | :--- |
| `0x20` | `1 byte` | `R/W` | Sets and reads the PWM duty cycle of the on-board blue LED |

#### Parameters

| Address/Offset | Value/Range | Default | Description |
| :--- | :--- | :--- | :--- |
| `0x20` | `0 ~ 100` | `0` | PWM duty cycle in `%`; `0` is off and `100` is maximum brightness |
| `0x20` | `101 ~ 255` | N/A | Clamped to `100` on write; subsequent reads return `100` |

The PWM frequency is approximately `1 kHz`. The setting takes effect immediately after the write and returns to `0` after a system reset.

### 4.4 Key State

| Address/Range | Length | Permission | Function |
| :--- | :--: | :--: | :--- |
| `0x11` | `1 byte` | `R` | Returns the real-time state of the on-board key |

#### Parameters

| Address/Offset | Value/Range | Default | Description |
| :--- | :--- | :--- | :--- |
| `0x11` | `0` | Runtime | Key released |
| `0x11` | `1` | Runtime | Key pressed |

The key input is active low; the firmware has already converted the level to the logical values above.

### 4.5 Key Event

| Address/Range | Length | Permission | Function |
| :--- | :--: | :--: | :--- |
| `0x12` | `1 byte` | `R/C` | Returns the most recent key event; cleared automatically after the read completes |

#### Event Definitions

| Value | Event | Description |
| :--- | :--- | :--- |
| `0x00` | `None` | No event pending |
| `0x01` | `Single Click` | Single click |
| `0x02` | `Double Click` | Double click |
| `0x03` | `Long Press` | Long press |

#### Default Detection Parameters

| Parameter | Default | Description |
| :--- | :--- | :--- |
| Debounce time | `20 ms` | A level change is confirmed only after the key level stays stable |
| Double-click interval | `300 ms` | Maximum time to wait for the second press after the first release |
| Long-press time | `1000 ms` | A long-press event is generated when the key is held for this duration |

These three parameters can be changed through the `0x30 ~ 0x35` I²C registers or the firmware software interface `user_key_configure()`. The event is cleared only after the data byte of `0x12` is actually read; writing only the register address, or reading only the first 1/2 bytes starting at `0x10`, does not clear it.

### 4.6 Key Timing

| Address/Range | Length | Permission | Function |
| :--- | :--: | :--: | :--- |
| `0x30 ~ 0x35` | `6 byte` | `R/W` | Configures key detection timing in `ms` |

| Address | Name | Format | Default | Description |
| :--- | :--- | :--- | :--- | :--- |
| `0x30 ~ 0x31` | `Debounce Time` | Little-endian `uint16_t` | `20 ms` (`14 00`) | Debounce time |
| `0x32 ~ 0x33` | `Double Click Time` | Little-endian `uint16_t` | `300 ms` (`2C 01`) | Maximum time to wait for the second press after the first release |
| `0x34 ~ 0x35` | `Long Press Time` | Little-endian `uint16_t` | `1000 ms` (`E8 03`) | Long-press event is generated after the key is held for this duration |

The parameters must satisfy all of: `Debounce Time > 0`, `Double Click Time > Debounce Time`, `Long Press Time > Double Click Time`. If not, the entire write is ignored and the previous configuration is kept.

Contiguous read/write may start at any address within the group, but a write must not go past `0x35`. Writing 6 bytes starting at `0x30` is recommended so that all three timing parameters take effect together. The configuration is valid only for the current run and returns to defaults after reset or power cycle.

### 4.7 MCU UID

| Address/Range | Length | Permission | Function |
| :--- | :--: | :--: | :--- |
| `0xE0 ~ 0xEB` | `12 byte` | `R` | Returns the factory-programmed 96-bit unique ID of the MCU |

The UID is read and cached during power-on initialization. When reading starts at any address within `0xE0 ~ 0xEB`, the firmware returns the corresponding UID bytes through `0xEB`. For example, at most 4 bytes can be read consecutively starting at `0xE8`.

The 12 bytes are arranged in the order of the STM32 UID's three 32-bit registers, with each 32-bit value stored in little-endian byte order. The UID is read-only; write requests are ignored.

### 4.8 IAP Upgrade

| Address/Range | Length | Permission | Function |
| :--- | :--: | :--: | :--- |
| `0xFD` | `1 byte` | `W` | Triggers a system reset so that the companion IAP upgrade flow takes over |

#### Parameters

| Address/Offset | Value/Range | Default | Description |
| :--- | :--- | :--- | :--- |
| `0xFD` | `0x00` | N/A | No operation |
| `0xFD` | `0x01 ~ 0xFF` | N/A | Triggers an MCU system reset after the write transaction completes |

#### Notes

1. This register only triggers a reset and carries no firmware data.
2. After a non-zero value is written, the current I²C session ends with the system reset.
3. To enter IAP, hold both SCL and SDA low during the reset. The bootloader samples both lines about `30 ms` after startup; if both are low, it provides an initial IAP wait window of about `500 ms`, otherwise it jumps back to the application.
4. The bootloader uses the fixed 7-bit I²C address `0x54`; its upgrade commands and data frames are outside the scope of this document.
5. After the reset is triggered, non-persistent application register state returns to defaults; the I²C address continues to use the value stored in flash.
6. Use the upgrade tool that matches this product to complete bootloader takeover and firmware transfer.

### 4.10 I2C Address

| Address/Range | Length | Permission | Function |
| :--- | :--: | :--: | :--- |
| `0xFF` | `1 byte` | `R/W` | Reads or changes the 7-bit I²C address of the current application firmware |

#### Parameters

| Address/Offset | Value/Range | Default | Description |
| :--- | :--- | :--- | :--- |
| `0xFF` | `0x08 ~ 0x77` | `0x3F` | Valid 7-bit I²C address; takes effect immediately after the write |
| `0xFF` | `0x00 ~ 0x07`, `0x78 ~ 0xFF` | N/A | Invalid address; the write is ignored and the current address is kept |

#### Notes

1. The new address takes effect after the current write transaction completes; the next transaction must use the new address.
2. A valid address is written to flash; the device continues to use the last saved address after a system reset or power cycle. If there is no valid record in flash, the default address `0x3F` is used.
3. Writing the same value as the current address does not trigger re-initialization.
4. Before changing the address, the host should confirm that the target address is not used by another device on the same bus.

### 4.11 X Accumulated Motion

| Address/Range | Length | Permission | Function |
| :--- | :--: | :--: | :--- |
| `0x06 ~ 0x09` | `4 byte` | `R` | Returns the X motion accumulated since the last clear |

The data format is little-endian signed `int32_t`. Reading does not clear it automatically; to clear it, write `0x01` to `0x41` (see `4.17`). Reading 8 bytes starting at `0x06` returns the X and Y accumulated values in order. New motion generated during the read is included in the accumulated value of the next read.

### 4.12 Y Accumulated Motion

| Address/Range | Length | Permission | Function |
| :--- | :--: | :--: | :--- |
| `0x0A ~ 0x0D` | `4 byte` | `R` | Returns the Y motion accumulated since the last clear |

The data format is little-endian signed `int32_t`. Reading does not clear it automatically; to clear it, write `0x01` to `0x41` (see `4.17`). The accumulated value uses saturation protection and does not wrap around.

### 4.13 Sensor Init Status

| Value | Status | Description |
| :--- | :--- | :--- |
| `0x00` | `Success` | MOT6010 initialized successfully and can sample normally |
| `0x01` | `Failed` | MOT6010 initialization failed; sampling stopped |
| `0x02` | `Initializing` | Initialization in progress or a re-initialization request is waiting for the main loop |
| `0x03` | `Reserved` | Reserved |

At power-on, up to 3 initialization attempts are made; there is no periodic retry. After the re-initialization command runs once, this register updates to success or failure.

### 4.14 Sensor Reinitialize

| Written value | Behavior |
| :--- | :--- |
| `0x01` | Requests the main loop to re-initialize the MOT6010 |
| Other values | Ignored |

The command is executed asynchronously by the main loop; it does not block the internal sensor bus inside the external I²C callback. When re-initialization starts, the most recent `DX/DY`, `Data Ready`, X/Y accumulated values and the old polling state are cleared; whether initialization finally succeeds or fails, motion data from before initialization is not retained.

`0x40` and `0x41` (write-only) form a contiguous write group: when 2 bytes are written consecutively starting at `0x40`, the two registers are validated and processed separately, so re-initialization and the `0x41` clear command can be requested together; if the data for one register is invalid, only that register is ignored. A standalone write starting at `0x41` is still handled according to `4.17`. Both registers are write-only; reads return `0xFF`.

### 4.15 Axis Configuration

| Address/Range | Length | Permission | Function |
| :--- | :--: | :--: | :--- |
| `0x50` | `1 byte` | `R/W` | User-level X/Y direction and swap configuration |

| Bit | Name | `0` | `1` |
| :--- | :--- | :--- | :--- |
| `bit0` | `X_INVERT` | X not inverted | X inverted |
| `bit1` | `Y_INVERT` | Y not inverted | Y inverted |
| `bit2` | `XY_SWAP` | X/Y not swapped | X/Y swapped |
| `bit3 ~ bit7` | `Reserved` | Must be `0` | Write ignored |

The default value `0x00` means the user-level X/Y are neither inverted nor swapped. The firmware automatically maps the user coordinates to the sensor's internal coordinates and always keeps 12-bit mode. The configuration is applied in the main loop; writes with invalid reserved bits are ignored. If configuration fails but rollback succeeds, the currently effective values stay unchanged; if the configuration state cannot be recovered, the initialization status becomes failed, sampling stops and motion data is cleared, waiting for re-initialization via `0x40`. After the configuration value changes and takes effect successfully, the firmware clears the most recent `DX/DY`, `Data Ready` and X/Y accumulated values to avoid mixing coordinate data from before and after the switch. Writing the current effective configuration again does not clear data.

`0x50` and `0x51` (error count) form a contiguous read/write group: reading 2 bytes starting at `0x50` returns the axis configuration and the error count in order; when 2 bytes are written consecutively starting at `0x50`, the two registers are validated and processed separately, so the axis configuration can be set and the error count cleared at the same time. Only writing `0x00` to `0x51` clears the count; any other value only ignores this write to `0x51` and does not affect processing of `0x50`.

### 4.16 Sensor I2C Error Count

| Address/Range | Length | Permission | Function |
| :--- | :--: | :--: | :--- |
| `0x51` | `1 byte` | `R/W` | Cumulative number of failed I²C read/write transactions to the internal MOT6010 |

| Operation | Behavior |
| :--- | :--- |
| Read | Returns the cumulative number of failed I²C read/write transactions to the internal MOT6010; not cleared automatically |
| Write `0x00` | Requests the main loop to clear the error count |
| Write other values | Ignored |

The counter holds at `0xFF` and does not wrap around. It counts failed I²C read and write transactions to the internal MOT6010, including initialization and runtime access; it does not count I²C2 transactions from the external host to this device. If the sensor returns an unexpected value but the I²C transaction itself succeeds, it is not counted as a communication error. The clear request is handled by the main loop to avoid modifying the error count concurrently with internal access. `0x51` and `0x50` (axis configuration) form a contiguous read/write group; see `4.15`.

### 4.17 Clear Data

| Address/Range | Length | Permission | Function |
| :--- | :--: | :--: | :--- |
| `0x41` | `1 byte` | `W` | Explicitly clears accumulated motion or motion data |

#### Command Definitions

| Written value | Operation |
| :--- | :--- |
| `0x01` | Clears X/Y accumulated motion (`0x06 ~ 0x0D`) |
| `0x02` | Clears the most recent motion data `DX/DY` and `Data Ready` (`0x00 ~ 0x03`, `0x10`) |
| Other values | Ignored |

#### Notes

1. The clear operation is executed asynchronously by the main loop; it does not block the internal sensor bus inside the external I²C callback.
2. Writing `0x01` clears only the accumulated motion and does not affect the most recent `DX/DY` or `Data Ready`; new motion generated after the clear is accumulated normally.
3. Writing `0x02` clears both the most recent `DX/DY` and `Data Ready`, avoiding the inconsistent state where `DX/DY` are zero but `Data Ready` is still `1`; it does not affect the accumulated motion.
4. The accumulated motion registers are read-only and are no longer cleared automatically on read; they must be cleared explicitly through `0x41`.
5. This register is write-only; reads return `0xFF`.
6. `0x41` and `0x40` (re-initialize) form a contiguous write group; see `4.14`.

## 6. Usage Examples

### 6.1 Reading Motion and Ready State

The host first performs a 1-byte read from register address `0x10` and confirms that it returns `01`. It then performs a 4-byte contiguous read from `0x00`, assuming the response is:

```text
05 00 FD FF
```

Parsed result:

| Field | Raw data | Parsed value |
| :--- | :--- | :--- |
| `DX` | `05 00` | `5` |
| `DY` | `FD FF` | `-3` |
| `Data Ready` | `01` | New data available (read separately from `0x10`) |

`Data Ready` has already been cleared automatically after the `0x10` read above; the host does not need to write an acknowledgment.

### 6.2 Setting LED Brightness

Write decimal `50` (`0x32`) to `0x20` to set the LED PWM duty cycle to about `50%`:

```text
20 32
```

### 6.3 Changing the Runtime I²C Address

When the device's current address is `0x3F`, write `0x40` to `0xFF`:

```text
FF 40
```

After this transaction completes, the device immediately switches to the 7-bit address `0x40`; after a reset it continues to use `0x40` stored in flash.

## 7. Error and Boundary Behavior

| Scenario | Device behavior |
| :--- | :--- |
| Read from a reserved or unimplemented address | Returns `0xFF` |
| Contiguous read beyond the end of the current register group | The excess part returns `0xFF` |
| Write to a read-only, reserved or unimplemented address | Write ignored; device state unchanged |
| Non-group write transaction whose length is not 2 bytes | No register write operation is performed |
| Register group write beyond the group end | Entire write ignored; previous values retained |
| Key timing write beyond `0x35` or invalid parameter relationship | Entire write ignored; previous configuration retained |
| Write to an invalid I²C address | Write ignored; current address retained |
| I²C write transaction does not terminate normally | The firmware attempts to recover the I²C slave peripheral after about `500 ms` |
